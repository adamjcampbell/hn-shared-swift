# ADR-0019: Compose the core from isolation-threaded free functions; vend one `Core`, compose `SendMessageAction` at the app boundary

## Status

Accepted (2026-06-01). Supersedes [ADR-0015](0015-engine-borrows-host-executor.md) and [ADR-0016](0016-engine-actor-flat-model.md).

Amended by [ADR-0021](0021-spawn-owning-task-registry.md) (2026-06-12): the isolation-threaded free-function parameters and the `inout` registry described below are replaced by a spawn-owning `TaskRegistry` class; the one-`Core` handle, the `SendMessageAction` boundary, and the sole-writer discipline stand.

Revised 2026-06-02: the outer `@MainActor UICore` struct was dissolved. A pressure-test established that two structs were not forced by isolation — the only difference between the consumers is the send capability, and that can be composed at the app boundary. One isolation-generic `Core` is now the single vended (and bridged) handle; production builds the `@MainActor` `SendMessageAction(core)` itself. The free-function core below is unchanged; only the "outer layer" decision is revised, and the original two-struct form is recorded under *Alternatives considered*.

## Context

[ADR-0015](0015-engine-borrows-host-executor.md) made `Engine` a `final actor` that borrowed its executor from an `isolation: any Actor` initializer parameter (SE-0392): production passed `MainActor.shared` so calls were virtual hops, tests passed a `TestActor` for per-test parallelism. [ADR-0016](0016-engine-actor-flat-model.md) made that actor the sole writer of a flat `@Observable` `Model`.

The actor bought one thing: a single isolation region that serialised every `Model` and task-registry write and satisfied region isolation (SE-0414) for the non-`Sendable` `Model`. It cost an `unownedExecutor` property, a `nonisolated(unsafe)` rebind to lift `Model` out of the region into the `@MainActor` handle, and a layer of indirection between the factory and the code that actually mutates state.

An experiment showed the region can be established without an actor type. Threading `isolation: isolated any Actor = #isolation` (SE-0420) through plain functions, then referencing that parameter inside every spawned `Task { … }`, captures the isolated parameter so the work runs on the host actor; the writes stay serialised there. Referencing the parameter is required, not decorative: a bare `Task { }` infers `@concurrent`, runs on the global executor, and fails to compile against the non-`Sendable` `Model` capture. The composition then happens directly in the factory rather than inside an actor's methods.

Two pressures still have to be reconciled, the same two [ADR-0015](0015-engine-borrows-host-executor.md) named: production wants the bridged surface pinned to `MainActor` ([ADR-0014](0014-mainactor-both-platforms.md)); tests want their own executor so the suite parallelises. The free-function form resolves this by vending one isolation-generic `Core` and composing the `@MainActor` send capability at the app boundary, instead of by borrowing an executor.

## Decision

**The `Core` handle (isolation-generic).** A `Core` struct bundles the `Model`, the `AsyncStream<Command>`, a `(Message) async -> Void` send closure, and a `cancelAll` hook. `makeCore(model:isolation: isolated any Actor = #isolation)` builds the command stream and a local `var tasks` registry, spawns the search listener inline, and returns the handle. The message handling is free functions — `apply(_:to:commands:tasks:isolation:)`, `applySearchQuery(...)`, and `fetch(...)` — each threading `#isolation`.

The struct is `public` and `// SKIP @bridgeMembers`: it is the single handle every consumer holds. Only `model` and `commands` are `public` and cross JNI; `sendMessage` and `cancelAll` are `internal` + `// SKIP @nobridge`, so app code reaches the send capability only through the `@MainActor` `SendMessageAction` that wraps it, while tests in-module call the raw closure (and `cancelAll`) directly.

Three details make this work:

- **`apply` is synchronous and returns the in-flight `Task`.** It mutates `Model` and `tasks` and returns; the send closure awaits `…?.value` *outside* the `inout tasks` access. This is the load-bearing invariant. The host actor serialises *execution steps*, not whole handlers, so an `await` inside the read-modify-write window would let actor reentrancy interleave a second handler and lose updates. A synchronous `apply` cannot span a suspension, so each handler's mutation stays atomic on the actor and the `inout tasks` access cannot overlap the listener's access to the same box.
- **The listener is inlined in `makeCore`, not extracted into a `bind(tasks: inout …)` function.** An escaping closure cannot capture an `inout` parameter, so a listener `Task` that mutates `tasks` has to close over the *local* `var`. The listener, the send closure, and `cancelAll` all capture that one box; every one of them runs in `isolation`'s region, so the non-`Sendable` captures stay serialised.
- **The send closure is a plain `(Message) async -> Void`, left non-`Sendable`.** It captures the `Model` and the `tasks` box, so the type system forbids sending it across isolation domains: every caller is confined to the region `makeCore` was formed on, and the body runs on that host actor — `MainActor` in production, a `TestActor` in tests. Concurrent UI callers — a fire-and-forget tap plus a `.refreshable` — serialise at the `@MainActor` `SendMessageAction` that wraps it, not at this closure. Typing the closure `@isolated(any)` to pin it to its formation actor was tried and dropped: the non-`Sendable` confinement already guarantees the body runs on the host, so the pin is never observable, and adding `@Sendable` later would strip the dynamic isolation to `nil`. Referencing `isolation` in the body stays required — it is what makes `#isolation` in `apply` resolve to the host (drop it and `#isolation` is `nil`, which `apply`'s non-optional `isolated any Actor` rejects).

**Production entry (`@MainActor`, bridged).** `makeAppCore()` is `@MainActor` and `// SKIP @bridge`; it calls `makeCore()` (so `#isolation` resolves to `MainActor.shared`) and returns the `Core`. It is the only function that crosses JNI. There is no second struct: the app composes the send capability from the handle with `SendMessageAction(core)` — iOS installs it into `@Environment(\.sendMessage)`, Android builds it once with `remember(core) { SendMessageAction(core) }`. The `@MainActor` boundary from [ADR-0014](0014-mainactor-both-platforms.md) is unchanged; it now lives on `SendMessageAction` rather than a wrapper struct.

`SendMessageAction(_ core:)` is `@MainActor` so it can capture the non-`Sendable` `core` in-region into its `@MainActor` stored closure. `@MainActor` on the entry points (`callAsFunction`, `send`, `run`) states the capability's contract where callers read it and bridges to Android as a main-thread assertion, so an off-main call from Kotlin traps rather than mutating `Model` off-region; `send`'s `Task { … }` inherits that main actor (no explicit `@MainActor in`), preserving fire-and-forget call order. Its `Equatable` discriminates only live from no-op (a small `Kind` enum): exactly one live action is ever installed, so the environment diff needs only to tell the real action from the previews/defaults no-op — the `Model`-identity comparison the previous wrapper used was defending against a case that never occurs. Android never consults `Equatable`; the bridge compares the peer object by identity, which is why the Android site builds the action once via `remember`.

**Tests.** A `withCore` fixture is isolated to a per-test `TestActor` and calls `makeCore()` so `#isolation` binds there. There is no `Engine`, no `unownedExecutor`, no `nonisolated(unsafe)` rebind. Each test gets its own actor and queue, so the suite still parallelises across instances.

**Carried forward from [ADR-0016](0016-engine-actor-flat-model.md).** `Model` stays a flat `@Observable final class` with one field per axis; new state lands as a new field plus one arm on the `apply` switch. The `apply` free functions are the sole writers — the discipline that was "`Engine` is the only writer" now reads "only `apply` mutates `Model`". No mutators on `Model`.

## Consequences

- No actor type, no borrowed executor, no `nonisolated(unsafe)` rebind anywhere in the core target. Isolation is threaded by the compiler through `#isolation` and packaged at the `@MainActor` boundary in `makeAppCore` / `SendMessageAction`.
- Serialisation of concurrent callers comes from the `@MainActor` `SendMessageAction` boundary plus the synchronous `apply`, not from the `Core.sendMessage` closure's type. The previous actor gave the boundary for free through its mailbox; the free-function form establishes it on `SendMessageAction`'s `@MainActor` entry points.
- The `withCore` body runs as one isolated scope, so the `run { isolated engine in … }` batching helper from the actor era is gone — reads and `sendMessage` calls in a test body already share a consistent snapshot between suspension points. A `settle` helper drains the `TestActor` twice where a `model.searchQuery` write must be observed: `AsyncStream` schedules the listener's resume as a new job behind the one already running, so a single drain returns before the listener runs. Two is the minimal deterministic count on a serial queue — job ordering, not a load-dependent race.
- The cost of dropping the actor: `Core.sendMessage` no longer advertises its isolation the way an `actor` method signature did, so it reads as callable from anywhere. What keeps it safe is the non-`Sendable` capture (the compiler rejects any off-region call) and its `internal` visibility (app code can't see it); production only ever calls it through the `@MainActor` `SendMessageAction`.
- One vended handle. `Core` is what tests and both platforms hold; production additionally composes a `SendMessageAction(core)` at the app boundary. The `@nobridge` annotations on `sendMessage` / `cancelAll` are load-bearing — a non-bridgeable member added to the public `Core` without one would break the Android build. Acceptable: `HackerNewsReader` is a first-party app core, not a published SDK.
- One composition root. `makeCore` is where the state, the stream, the registry, the listener, and the send capability are wired together, top to bottom, instead of split across an `init`, a `bind()`, and a set of actor methods.

## Alternatives considered

**A `Sendable`, host-generic send closure via `@_inheritActorContext`.** Rather than leave the inner `sendMessage` non-`Sendable` and promote to `MainActor` at the boundary, the closure can be made `@Sendable` (and, redundantly, `@isolated(any)`) directly, by routing it through a `Core.init` parameter annotated `@_inheritActorContext`. This compiles and runs correctly: the closure stays isolated to the host actor `makeCore` was formed on (`MainActor` in production, a `TestActor` in tests), captures the non-`Sendable` `Model` and the `tasks` box by isolation-match, serialises with no lost writes, and hops home when invoked from a foreign isolation. It would make the `Core.sendMessage` capability `Sendable` and remove the `{ @MainActor in … }` wrapper from `SendMessageAction(_:)`.

Rejected. `@_inheritActorContext` is an underscored attribute; the Swift repository's underscored-attributes reference marks all such attributes strongly discouraged outside the standard library, with semantics that may change ahead of any evolution review. Its behaviour is also a documented footgun: it inherits isolation only when the closure explicitly captures the isolated parameter. For a closure capturing only `Sendable` state, omitting that capture silently falls back to the global concurrent executor; this variant's non-`Sendable` `Model` / `tasks` capture would instead make the omission a compile error, but the underscored-attribute risk stands regardless. The Swift team has described this as "very subtle" and an open question, and the surrounding `nonisolated(nonsending)` inference for `@Sendable` closures has shifted across recent point releases. Consuming the attribute transitively through `Task.init` (stable, evolution-reviewed API) is fine and is what the spawned `Task { _ = isolation; … }` already does; authoring a public surface that depends on it is the discouraged usage. The boundary this design needs is `MainActor` regardless — the UI is `MainActor` — and the `@MainActor` entry points on `SendMessageAction` state that with stable features; tests call `sendMessage` directly from the `TestActor`-isolated body and never need a `Sendable` crossing.

**A second `@MainActor UICore` struct bundling `Model` + commands + `SendMessageAction`.** The originally-accepted form (2026-06-01): keep `Core` `internal` and isolation-generic, and vend a separate `public @MainActor struct UICore` built by `makeUICore()`, which pre-wraps the send closure in a `SendMessageAction` once. The pressure-test that prompted this revision confirmed it works and reads cleanly, but found it is not forced: the two structs share `model` and `commands`, and `UICore` is just `Core` with the send field swapped (closure → action) and `cancelAll` dropped. The decoupling it appears to buy — keeping the engine handle off the public/JNI surface — is delivered instead by member visibility (`internal` + `// SKIP @nobridge`) on the one `Core`. Two further candidates were measured and rejected: collapsing the inner handle to a named-tuple typealias (−9 LOC but it deletes the per-field DocC and demotes `Core.searchDebounce` out of its namespace), and having `UICore` hold a `Core` behind computed forwarders (a net +1 member plus a `@nobridge` annotation — a regression). Dissolving `UICore` and composing `SendMessageAction(core)` at the two app sites is the smaller, more honest surface; the only cost is the one-line `remember(core)` on Android (iOS absorbs reconstruction through `Equatable`).
